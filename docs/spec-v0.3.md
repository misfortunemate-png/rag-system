## 3. 技術選定

| 技術 | 理由 |
|---|---|
| pdfplumber＋PyMuPDF突合 | 得意分野が補完的。テキスト層PDFに対し誤読ゼロ |
| MinerU hybrid（帳票） | CJKレイアウト解析の定番。VRAM要件をRTX 5060 Ti 16GBが充足 |
| LlamaIndex | 検索層のみ使用 |
| エージェントループ自前実装 | デモの核はトレースの説明可能性。フレームワークのAgent抽象は挙動がブラックボックス化するため不採用 |
| Chroma | ローカル・無料。domainメタデータフィルタで系統別検索 |
| ruri-v3-310m | 日本語検索精度。プレフィックス必須（§3制約） |
| LLMバックエンド切替式 | OpenRouter（OpenAI互換）／Anthropic直の2アダプタ。環境変数でプロバイダ・モデル指定（§3.1） |
| Streamlit | 完成速度優先。React化は将来課題 |

### §3.1 LLMバックエンド

- 環境変数:
  - `LLM_PROVIDER`：`openrouter`（既定）／`anthropic`
  - `LLM_MODEL`：モデルID（例：`qwen/qwen3-235b-a22b`、`deepseek/deepseek-chat-v3.1`、`claude-haiku-4-5-20251001`）
  - `OPENROUTER_API_KEY`／`ANTHROPIC_API_KEY`：使用プロバイダのもののみ必須
- src/llm.py にアダプタ2実装。ツール定義はプロバイダ非依存の内部形式で持ち、アダプタがAnthropic native／OpenAI互換の各形式に変換する
- 制約: 選択モデルはツール使用（function calling）対応であること。トレース形式はプロバイダに依存しない共通スキーマとする
- 既定モデルは実装時点でOpenRouter上のコスト最適なツール対応モデルをPGが確認して仮置きし、READMEに選定根拠を記載（モデル価格は変動するため本書に固定値を書かない）

## 4. 機能仕様

### §1 extract（突合抽出）
- 何を: 2エンジン（帳票は＋MinerU）で抽出し、arbiterが最良結果を採用
- どのように: 判定は文字数・文字化け率（U+FFFD・制御文字出現率）・行断片化度の多軸。採用エンジンと理由をログに残す
- 制約: 判定基準と閾値はREADMEに明文化

### §2 chunker
- 何を: データ定義v0.4の分割ルールを実装
- どのように: 条番号正規表現で階層解析、閾値ルールで統合・分割。本文中の条文間参照（「X.Y.Z「…」による」等）を決定的抽出しrefsに格納、全エッジをdata/refs.jsonlに出力
- 制約: 中間JSONLを出力し、Chroma投入前に目視検査可能にする

### §3 ingest
- 何を: documents.yamlに従い複数文書を埋め込み・格納
- どのように: ruri-v3-310m。埋め込み対象はheading＋body連結。domainをメタデータに付与
- 制約: クエリ側／文書側プレフィックスはHuggingFaceモデルカードを正として実装時に照合し、付与漏れをユニットテストで検査（付け忘れが最大の既知の罠。不確かな仕様を本書に書き写さない）

### §4 agent（ツール使用ループ）
- 何を: 質問に対し、ツールを繰り返し呼びながら回答を構成する
- どのように: Claude APIのツール使用。ツールは2本のみ
  - `search_chunks(query, domain=None, top_k=3)`：ベクトル検索。domainでフィルタ可
  - `read_section(doc_slug, hierarchy)`：階層指定で条文全文を返す
- システムプロンプト要点: 出典の章・条番号を必ず明示／根拠がなければ「該当なし」／検索結果の要約でなく原文照合に基づいて答える／検索結果のrefsに参照先がある場合、回答に必要ならread_sectionで参照先を精読する（参照追跡。トレースに記録される）
- 制約: 最大ループ回数10（暴走防止）。全ツール呼び出しと引数をトレースとして記録し、UIとevalの両方から参照可能な形式（JSONL）で保存

### §5 crosscheck（横断モード）
- 何を: 複数系統に跨がる質問で観点分解→系統別検索→突合→統合要約を行う
- どのように: エージェント自身が観点分解を宣言（分解結果をトレースに記録）→ domainフィルタ付きsearch_chunksを系統ごとに実行 → 突合ステップで「整合／要調整」を判定し、要調整には根拠条項のペアを必須とする
- 制約: 横断モードは自動判定（質問が単一系統で完結するなら通常ループのまま）。判定もトレースに残す

### §6 eval
- 何を: 単一文書10問＋横断シナリオ1本を一括実行
- どのように: データ定義v0.3の評価レコードを出力。横断はexpected_conflict（要調整の検出）を合否基準とする
- 制約: pass判定は人間（ショウゴさん）。検査の最終責任を機械に渡さない構成自体を展示する

### §7 UI（Streamlit）
- 何を: チャット＋エージェント動作トレース＋根拠パネル
- どのように: 
  - レイアウト: 左カラム＝チャット、右カラム＝根拠パネル（引用条文の原文・ページ番号）
  - トレース: ツール呼び出しをストリーミングで逐次表示（検索→精読→照合→追加検索）
  - 出典チップ: 回答内の条番号をチップ表示、クリックで根拠パネルの該当条文へ
  - 横断時: 系統別カード（2×2）＋突合パネル（整合＝青／要調整＝黄のピル）＋統合要約
- デザイン指針: 青×白基調（承認済みモックアップ2点を正とする。mockup-multi-spec.html参照）。装飾より「動きが見える」ことを優先
- 制約: モックアップの数値・条番号は架空。実装時は実データのみ表示

## 5. テスト方針

| テスト対象 | 方法 | 合格条件 |
|---|---|---|
| 分割品質 | char_count分布と中間JSONL目視 | 断片・巨大チャンクが説明可能な範囲 |
| プレフィックス付与 | ユニットテスト | クエリ／文書両側に正しく付与 |
| M1: agent query | eval 10問 | 7問以上pass |
| M2: UI | 手動（M1と同じ質問） | UI上で動作しGIF撮影可能 |
| M3: 横断 | scenario 1本 | 観点分解・要調整検出・統合要約が動作 |
| M4: 帳票 | 手動実演 | 表構造がチャンク化され検索ヒット |

## 6. PG向け作業指示

素材PDF確定後、マイルストーンごとに指示書を作成する（R-014: 単一ファイル統合＋冒頭マニフェスト。配置は docs/instructions/）。M1の指示書から着工し、M2以降は前段の検査通過後に発行する。

実行環境の分担（2026-08-07裁定）: 全マイルストーンを自宅デスクトップ（i5-14400F / RTX 5060 Ti 16GB / 32GB RAM）で実施する。
