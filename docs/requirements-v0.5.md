# 規程エージェント 統合定義書 v0.5

作成日: 2026-08-05 ／ 最終改訂: 2026-08-07
PM: クリーデ ／ 承認: ショウゴさん

## 目的

副業参入用ポートフォリオ第一号。「仕様書・マニュアルに根拠付きで答えるエージェント」のデモを構築し、業務文書をAIに扱わせる際の意思決定をケーススタディとして展示する。

ショウゴさんのモチベーション維持を設計条件に含める。このため段階リリース（v1/v1.1/v1.2）を廃し、全機能を単一プロジェクトとしてマイルストーン順に構築する。各マイルストーンは単独でデモ可能であること（常にどこかが動いている状態を維持する）。

## コンセプト（30秒デモ）

画面は左にチャット、右に根拠パネル。質問するとエージェントの動作——検索→精読→照合→追加検索——がトレースとして流れ、条番号付きの回答と引用原文が並ぶ。根拠がなければ「該当なし」と答える。

複数仕様に跨がる質問（例：コンクリート埋込分電盤）では、観点分解→系統別検索→突合を実行し、仕様間の整合／要調整を色分け提示して統合要約する。横断デモの主役は各仕様の要約ではなく「仕様同士がぶつかる箇所の発見」。

## 成果物（5点）

1. 公開GitHubリポジトリ
2. デモUI（Streamlit：チャット＋動作トレース＋根拠パネル、青×白基調）
3. README＝ケーススタディ本体（設計判断・棄却経緯・失敗分析）
4. デモGIF（README冒頭・営業資料用）
5. 評価記録：単一文書10問＋横断1シナリオの検証ログ

## 機能要件

- **ingest**：複数の公開仕様書PDF → 突合抽出（pdfplumber＋PyMuPDF、帳票はMinerU）→ 条文構造単位のチャンク分割 → ローカルベクトルDB格納
- **agent query**：Claude APIのツール使用ループ。ツールは search_chunks（検索）と read_section（階層指定精読）の2本。単発RAGではなく質問分解・追加検索・照合の多段動作
- **横断モード**：複数系統に跨がる質問で観点分解→系統別検索→突合（整合／要調整の判定）→統合要約
- **帳票ingest**：スキャン帳票1〜2枚をMinerUで構造化抽出し、form型チャンクとして検索に載せる
- **UI**：エージェント動作トレースのストリーミング表示、出典チップ、根拠パネル（原文照合）、突合パネル（整合／要調整ピル）

## 非要件（やらないこと）

図面（CAD系）からのデータ抽出／文書更新の同期／運用自動化／認証・マルチユーザー／React実装（見栄えの上限より完成速度。磨き上げは将来課題）

## 素材（ショウゴさん選定）

- 単一文書デモ用：**公共建築工事標準仕様書（電気設備工事編）令和7年版**（確定・2026-08-07裁定。https://www.mlit.go.jp/gobuild/content/001888825.pdf ）
- 横断デモ用：同シリーズの建築工事編・機械設備工事編等、横断シナリオ1本が成立する最小セット（M3着手前に選定）
- 帳票デモ用：公開のスキャン帳票サンプル1〜2枚（点検様式に近いもの）

## プロダクト構成（確定）

| 工程 | 採用 | 備考 |
|---|---|---|
| PDF抽出 | pdfplumber＋PyMuPDF 突合 | 既存突合スクリプトの設計を流用 |
| 帳票抽出 | MinerU hybridバックエンド | RTX 5060 Ti 16GBでVRAM要件充足 |
| チャンク分割 | 自前ルールベース（条番号正規表現） | ドメイン知識の見せ場 |
| フレームワーク | LlamaIndex | 検索層。エージェントループは自前（下記） |
| エージェント | LLMツール使用ループ（自前実装） | ツール2本のみ。フレームワークのAgent抽象は使わない（挙動の説明可能性を優先） |
| LLMバックエンド | OpenRouter／Anthropic直の切替式 | 環境変数でプロバイダ・モデルを指定（chat-pwa同様の可換設計）。コスト最適モデルを随時選択できることを要件とする |
| ベクトルDB | Chroma | ローカル・無料 |
| 埋め込み | ruri-v3-310m | 日本語SOTA。プレフィックス必須（仕様書参照） |
| UI | Streamlit | 完成速度優先。デザイン指針は仕様書§7 |

## 棄却リスト（READMEに理由ごと記載）

- tesseract：日本語で実用不達（実試行済み）
- Docling：日本語の文字誤抽出報告
- YomiToku：精度最高クラスだがCC BY-NC-SA（商用別途ライセンス）。商用交渉可能な案件では再検討候補
- LlamaIndexのAgent抽象：デモの核はトレースの説明可能性であり、ループを自前で書く方が制御と展示価値が高い
- ハイブリッド検索・RAGAS：現規模に過剰。将来改善候補
- React UI：見栄えの上限は高いが完成速度と交換

## マイルストーン（この順に構築。各段でデモ可能）

| M | 内容 | 完成条件 |
|---|---|---|
| M1 | 単一文書ingest＋agent query（CLI） | 評価10問中7問以上pass（出典正・原文と矛盾なし） |
| M2 | Streamlit UI（トレース・根拠パネル） | M1と同じ質問がUI上で動作し、GIF撮影可能 |
| M3 | 複数文書ingest＋横断モード | 横断シナリオ1本で観点分解→突合→統合要約が動作 |
| M4 | MinerU帳票ingest | 帳票の表構造がチャンク化され検索ヒット |

未達分は失敗分析としてREADMEに記載する（追い込みより記述）。
